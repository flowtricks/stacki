# Interface languages (i18n)

Stacki's own interface (Desktop and Studio, which share `src/`) is translated with small per-language
catalogs loaded on demand. No runtime dependency: the platform already has `Intl.PluralRules`,
`Intl.NumberFormat` and `Intl.DateTimeFormat`, and a hand-rolled `{name}` formatter is under 200 lines
(AGENTS.md §17). This is interface translation, not multilingual-site features.

## Shipped

English (source), Spanish, French, German, Brazilian Portuguese: `LOCALES` in `shared/core/i18n/locales.ts`.

## Where things live

| Piece | Path |
|---|---|
| Locales, native names, `dir` | `shared/core/i18n/locales.ts` |
| Message types, `{name}` formatting, plurals, `createTranslator`, bounds | `shared/core/i18n/catalog.ts` |
| `parseLocale`, `parseLocalePreference`, `matchLocale`, `resolveLocale` | `shared/core/i18n/parseLocale.ts` |
| Catalogs: one directory per language, one file per namespace (`en/ai.ts`, `de/settings.ts`, ...) and an `index.ts` that merges them | `shared/properties/i18n/messages/<locale>/` (`en`, `es`, `fr`, `de`, `ptBR`) |
| Lazy loader, provider, hooks, stored preference | `src/lib/i18n/` |
| Language dropdown | `src/app/settings/LanguageSetting.tsx` (Editor settings, General) |

The renderer code sits in `src/lib/` and the shared code in `shared/core/` and `shared/properties/` because those
are the layers the source-layer lint already lists; a dedicated `i18n` layer would be a gate-file change.

## Keys

Stable dotted names, feature first, lowerCamel segments, at least two segments: `ai.composer.placeholder.send`,
`settings.editor.sound.label`. A key is never reused for different text; change the text, keep the key, and
the translations are re-reviewed. `isMessageKey` enforces the shape and `keyCharsMax`.

## Catalogs

Typed TS modules, never JSON cast to a type. A catalog is split by **namespace**, the first segment of the key, so each feature area owns
its own small file per language and parallel work never edits the same file:

```
shared/properties/i18n/messages/
  en/ai.ts  en/audits.ts  en/settings.ts  ...  en/index.ts     source of truth; en/index.ts defines MessageKey
  es/  fr/  de/  ptBR/                                          the same files, the same keys
```

```ts
// en/settings.ts: the keys must start with "settings."; the compiler rejects any other prefix.
export const messages = { 'settings.title': 'Settings' } as const satisfies CatalogOf<`settings.${string}`>;
export type MessageKey = keyof typeof messages;
// de/settings.ts: the compiler rejects a missing or extra key.
export const messages = { 'settings.title': 'Einstellungen' } as const satisfies CatalogOf<MessageKey>;
// en/index.ts and de/index.ts: spread every namespace into the one catalog the loader imports.
export const messages = { ...ai, ...audits, ...settings } as const satisfies CatalogOf<string>;
```

**To add strings:** add the key to `en/<ns>.ts` and to all four other locales' `<ns>.ts`, then use `translate()`. A key of a new namespace also
needs `en/<ns>.ts` plus the four translations, one `import` and one spread in each of the five `index.ts` files, and the new files listed in
`studio/scripts/shared-source.json`. Keep keys alphabetical inside a file.

`test/shared/properties/i18n/catalogParity.test.ts` holds the layout: every locale has exactly English's namespace files, a namespace file
holds only keys with its own prefix, every index merges exactly the keys of its files, every namespace has English's keys, and each translation
has English's placeholders per key.
Comment `// review` on any line a human should check.

Migrating the rest of the interface: **`docs/i18n-playbook.md`** has the exact recipes (rich text, plurals, numbers and dates, shared and main-process text), the namespace
ownership table and the scan tool; `docs/i18n-inventory.md` has the string counts per folder.

## Messages

- Interpolation: `translate('ai.composer.placeholder.send', { queueKey })` with `{queueKey}` in the text. `{{` and `}}` are literal
  braces. A malformed template (`{`, `}`, `{}`, `{bad name}`) is an error value, not a guess.
- Plurals: a message may be `{ one: '{count} file', other: '{count} files' }`. Category comes from `Intl.PluralRules`
  for the locale; `other` is required and is the fallback for a category the catalog lacks. `count` must be a finite number.
- Numbers and dates are never hand-formatted: `useFormat()` (`formatNumber`, `formatDate`, `formatRelativeTime`, `formatList`, `formatBytes`, `shared/core/i18n/format.ts`).
- Sentences with inline code or links: `useTranslateRich()` with `{slot}` and `<tag>` marks (`shared/core/i18n/richText.ts`). Text from `shared/` or the main process: `MessageRef`, `useTranslateRef()`, `useTranslateDescribed()`; main speaks through `translateMain` (`electron/lib/mainLocale.ts`).
- Missing key or broken translation: the English text is shown and an issue is reported (a once-per-key `console.warn` in the app;
  tests pass an `onIssue` that throws). The UI never shows a raw key. English itself failing to format is a programmer error and asserts.
- Limits live in `CATALOG_LIMITS` next to the code (`shared/core/limits.ts` is a gate file): messages per catalog, characters
  per message, placeholders per message, parameters per call.

## Locale choice

1. Stored preference (`localStorage` `stacki.locale`, written by the Language dropdown; absent means "System default").
   It is parsed at the boundary: anything that is not a shipped locale is ignored.
2. Else the system languages: `navigator.languages`, which Electron fills from `app.getLocale()` and the OS list. The first tag that
   matches a shipped locale wins: exact tag, then primary language (`es-MX` gives `es`, `pt-PT` gives `pt-BR`).
3. Else `en`.

## Loading

`loadCatalog(locale)` does a dynamic `import()` of a language's `index.ts` (all its namespaces in one separate chunk), caches successes, shares concurrent
imports, does not cache failures, and parses the module with `parseCatalog` before use. `LocaleProvider` renders English
immediately and swaps when the catalog arrives, ignoring a stale arrival. English users download nothing extra (English itself is bundled, so the first render never waits). Per-namespace chunks are possible later without changing
`useTranslate()`: the loader would import `<locale>/<namespace>` for the namespaces a screen needs and merge them.
`<html lang>` and `dir` follow what is on screen. Without a provider, components render English.

## Direction

Right to left is out of scope. `localeDirection` is the single place that would return `rtl`; it is exhaustive over `Locale`, so adding
a right-to-left language fails to compile until it is decided. CSS would need logical properties first.

## Studio

Studio mounts the same `LocaleProvider` (`studio/src/app/main.tsx`) and follows the browser's languages. The shared files are listed in
`studio/scripts/shared-source.json`. Studio has no Settings dialog yet, so it has no Language dropdown (see phase 2).

## Next phases

2. A Studio language control, and one stored preference shared by Desktop windows and Studio.
3. A policy scan that flags new raw JSX text and string `aria-label`/`title` in folders already migrated (a gate-file change, so it needs a human's approval).
4. Translation workflow: English change in a PR lists the keys to translate; translators edit one `messages/<locale>/<namespace>.ts`; `// review` lines are

6. Marketing site (stacki.build): reuse the shared catalog code, or keep its own copy, decided then.
7. Add `docs/enforcement.md` rows (`review`: translation quality and key naming; `test`: catalog parity, loader, provider). That page is a gate file.
