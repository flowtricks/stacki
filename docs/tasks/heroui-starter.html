Stacki HeroUI starter tasks

Add Start from HeroUI beside Start from shadcn in the Stacki fork. Desktop creates and opens an Astro site. In Desktop and Studio, users can insert the full public HeroUI React v3 catalog, edit component props and content, and change the light and dark theme in Variables. The generated site includes a style guide and an interactive component gallery.

The heroui_starter branch starts at local main, commit 5d4cd354. This plan records the source audit, implementation tasks, and verification results.

What ships

  • Desktop wizard. Pick a parent folder, enter a site name, see the read-only project path update, and choose npm or pnpm in Stacki's dropdown. npm is the initial choice. Show creation progress and open the site when setup finishes. A failed creation preserves the wizard inputs for retry.
  • Components. Provide one useful insertion per documented component shipped in the pinned public React package. Expose meaningful variants, defaults, and compound content through typed Astro props or slots. Include helpers such as Label and FieldError with the context they need to work. The catalog covers the free package. HeroUI Pro requires a separate licensing decision. React component catalog · Pro licensing
  • Variables. Expose the public theme settings for both modes in project CSS. Include shared settings once where they apply to both modes. Keep derived values linked to their inputs. Inventory documented component-level overrides as well and record which belong in the theme and which are per-component styles.
  • Generated pages. Open on Style Guide at / with a link to Example Components at /example-components. Both pages use the same project CSS. A Light / Dark control on the generated site changes the theme of the page and its overlays.

What the audit found

  • Stacki already has a folder picker, wizard handoff, request parser, creation logs, and staged generator for shadcn. The wizard opens the returned path through the normal project flow. Creation handlers share a log channel, so concurrent attempts can interfere unless the channel has one owner. Welcome screen · Project handlers · Staged generator
  • Desktop and Studio discover Astro files and resolve the same insertion recipes. The shadcn gallery exposes editable props and slots on Astro wrappers and renders interactive controls in React islands. A palette tile has its own preview route, so verify it separately from the interactive page. Desktop discovery · Studio discovery · Editable gallery pattern · Tile preview
  • Both editors read authored CSS custom properties. Declarations supplied only by dependencies or declared directly in Tailwind's @theme are outside the current variable scan. Project-owned declarations in ordinary CSS rules give the editor a source location it can write back to. CSS variable reader · Studio variable reader · Studio variable edits
  • The registry publishes matching @heroui/react@3.2.8 and @heroui/styles@3.2.8. The React tarball contains 73 component documentation pages. HeroUI requires React 19 and Tailwind 4. Those dependencies belong in the generated site. The pinned package docs and exports give the implementation a versioned baseline. Release notes · React manifest · Styles manifest · React tarball

1. Pin and build a disposable Astro site

Start with the Astro version supported by the checkout's Studio package. Pin compatible versions of Astro, @astrojs/react, React and React DOM 19, Tailwind 4 and its Vite plugin, and both HeroUI packages at 3.2.8. Record the registry integrity values and check the resolved React Aria and date peers. Wire the full documented CSS imports through one shared Astro layout. Put the initial theme on document.documentElement so portalled overlays inherit it.

Pass when npm and pnpm each install and resolve the same intentional dependency set, the site builds and serves production output, and a hydrated Button renders with the expected styles without console or hydration errors. Record the actual installed versions and explain any additional dependency. HeroUI quick start · Astro React integration · Astro Tailwind integration

2. Prove the editing workflow on four components

Add Button, Card, Text Field, and Modal wrappers to the site. Use them to prove literal props and variants, named slots, a saved field default, and a portalled control. Add insertion recipes keyed by project-relative Astro paths in .stacki/components.json. Keep compound parts, controlled state, and callbacks in one React island. Pass serializable values through Astro. Hydrate the controls that need interaction.

Pass when both editors discover and insert all four, and the resulting Astro source contains the expected imports, props, and slot content. Edit a label, slot, and default, then reload and confirm each saved edit. Typing in a live field leaves the source intact. Open the Modal by keyboard, verify focus containment and themed overlay styles, close it with Escape, and verify focus returns to the trigger. Check the palette tile separately. Fix any blocker here before expanding the catalog. Recipe contract · Astro client directives

3. Expose and verify the full theme

Compare the official theming reference with dist/themes/default/variables.css and dist/themes/shared/theme.css in the pinned styles tarball. Keep a versioned inventory of shared, light, and dark settings. Cover semantic colors, surfaces, overlays, field and focus styles, spacing, radii, typography, shadows, and other documented public settings. For each entry, record its selector, expected value or expression, and where users edit it.

Write the public source settings into ordinary project CSS rules. Verify the cascade after the library import and keep Tailwind mappings and calculated values connected to their inputs. Provide a document-level light/dark control. Preserve an explicit choice across navigation and reload. Check the actual theme selectors against both editors and against portalled content.

Pass when every inventory entry has a disposition and each public theme setting can be changed in the intended mode. Test an accent color, an overlay color, a radius, a font setting, and a derived hover color. In each editor, compare the CSS before and after a save, then reload and verify the computed value in the matching mode. Changing a dark declaration leaves the light declaration intact. An alias keeps resolving after its source value changes. HeroUI theming · Dark mode · Styles tarball

4. Ship the full component catalog

Build a checked-in manifest from the pinned tarball's component documentation slugs. Compare it with the pinned React exports and the official Free catalog. Record discrepancies with their source and rationale. Map every component to an Astro wrapper, insertion recipe, gallery demo, and test case. Check for duplicate names, missing files, invalid slots, cyclic references, and recipe limits.

Develop and verify by component family. Give overlays, selections, date controls, and forms early coverage. In particular, test Select inside a Modal, two independent instances of a controlled collection, a date range encoded as serializable inputs, and validation with the correct accessible label and error. Use context-aware demos for components that depend on a form, group, or trigger.

Pass when the manifest, Components panel, and gallery agree with the pinned public inventory. Every recipe parses, inserts, builds, and renders. Representative interactions per family work in production output. Changing a saved default takes effect on reload, and preview interactions leave that default intact. A coverage test reports missing or unexpected entries when the package pin changes. shadcn inventory pattern · Recipe parsing and limits · HeroUI composition

5. Build the generated style guide and gallery

Create the shared layout and both Astro routes. Show theme colors, typography, spacing, radii, and representative states on Style Guide. Generate Example Components from the same manifest as the insertion recipes. Use the editable wrappers in the examples so changes in the inspector affect the same components users insert on their own pages. Use an accessible theme control and readable category navigation.

Pass when both pages appear in the Stacki page tree, navigation and theme switching work in the built site, and representative cards remain usable on a narrow viewport and with the keyboard. Both pages render after a fresh install. The gallery links and examples cover every manifest entry. shadcn generated layout and routes

6. Add the shared starter request

Read the shared contract before editing IPC. Extend project:createStarter with a HeroUI discriminator and shared location fields. Reuse the site-name, absolute parent-path, and package-manager parsers. Preserve the existing success reply and the legacy omitted-discriminator Lumos behavior. Keep starter-specific options on their own variants. Update the welcome bridge and handler through the existing request path.

Pass when contract tests accept valid HeroUI input for both managers and retain the Lumos and shadcn cases. Reject unknown starters, unsafe names, missing or relative parent paths, unsupported package managers, over-limit values, and shadcn options on a HeroUI request. Shared contracts · Starter request parser · Existing contract tests

7. Generate and publish the site safely

Write the versioned template into a staging directory under the canonical parent. Reuse existing bounded command and package-manager handling where the behavior matches. Isolate installation from any parent workspace. Write the app files and tracked .stacki metadata, verify the selected lockfile and manifest, and create and verify the initial Git commit before publishing. Ignore only generated .stacki/preview/ within the metadata directory.

Claim the destination without overwriting files. Define what happens if publication fails partway through, including how a failed rollback preserves the files needed for recovery. Stop the subprocess before cleanup. Give creation attempts one owner for the shared log and progress stream and release that ownership on success and failure.

Pass when generator tests cover missing tools, install or Git failure, timeouts, symlink parents and destinations, destination races, a partial move, failed rollback, retry, and concurrent requests. Test successful creation with both managers under an existing workspace. Confirm the published directory still installs and builds after relocation and Desktop detects the selected package manager. Staged creation and publication · Command runner · Generator test patterns

8. Connect the Desktop wizard

Add Start from HeroUI to the Welcome menu and connect it to the folder picker. Reuse the existing site name, path preview, package-manager Dropdown, and progress patterns. Add translated UI strings. Pass the successful project path to the existing open action. Report the failed creation step in the wizard with the option to retry.

Pass when keyboard users can pick HeroUI, choose a package manager, and create a site. Cancelling the picker leaves the welcome screen ready for another choice. An invalid name stays editable. An install failure retains the entered name and selected manager. Success opens Style Guide, and Desktop can reopen the published path through Open from folder. Check the existing Lumos, Astro, and shadcn choices. Welcome starter actions · Wizard pattern · Translation guidance

9. Verify the shipped workflow

  • Create sites through Desktop with npm and pnpm in clean directories. Include a parent path with spaces. Confirm each project opens, both routes build, Git captures the generated source, and a failed install can be retried without inheriting a partial site.
  • Run astro-studio check-project <project-directory> using the installed Studio CLI against each generated project. Fix missing component paths, invalid slots, and cycles together. Open the Desktop-hosted Studio and a standalone Studio draft and verify that each saves to the expected workspace. Studio modes and project check
  • In Desktop and Studio, exercise palette discovery, insertion, inspector edits, named slots, undo and redo, a saved default after reload, and two independent interactive instances. Reopen the saved project and compare the authored Astro and CSS with what the preview shows.
  • Compare light and dark in the built site and in interactive preview. Verify focus, Escape, and computed overlay styles on a portalled control. Confirm a Variables edit targets the matching declaration and leaves unrelated source intact. Check the palette tile for the intended theme.
  • Run npm run check:changed and env -u ELECTRON_RUN_AS_NODE npm test for the implementation. Record results for supported macOS, Windows, and Linux jobs, the package managers exercised, the catalog coverage result, and any checks that still need a run. Use the normal repository hooks. Repository checks · Enforcement

The starter is ready when a user can create and reopen a HeroUI site, insert every catalog entry, use its interactions in preview, and save theme changes in both editors. The four-component fixture is the first evidence for that workflow.

Pilot results

  • On macOS with Node 22.23.5, a disposable Astro 7.3.8 project with HeroUI 3.2.8 built with both npm and pnpm. The production page rendered Button, Card, Text Field, and Modal. Reloading restored the authored field default. Modal used the active theme, held focus while open, and returned focus to its trigger after Escape.
  • Desktop and standalone Studio discovered the pilot's Astro wrapper and inserted its configured props and slot text. Desktop saved a dark variable to the project. Standalone Studio saved the same kind of edit to its draft and preserved the source project.

Generated starter results on macOS

  • The built Desktop app created npm and pnpm sites through Start from HeroUI and opened Style Guide in the canvas. Desktop discovered all 73 wrappers in each site and saved a dark overlay variable without changing the light declaration.
  • npm and pnpm sites built after publication and a locked reinstall. Each kept its selected lockfile, recorded matching direct dependency versions, and contained one initial Git commit. Both passed astro-studio check-project.
  • Both production galleries contained all 73 audited examples and their projects had 73 insertion recipes. In Chromium, the gallery hydrated 56 islands. Tabs changed selection, dark mode persisted after a reload, Select worked inside Modal, and Escape restored focus to the trigger. The gallery fit a 390-pixel viewport.
  • The generated site's Astro React integration requires Node.js 22.23.4 or later. The project manifest and generated README record that minimum.
  • Standalone Studio opened a generated project's interactive preview and changed the HeroUI Pin item toggle from unpressed to pressed. Vite served the linked React and HeroUI modules while refusing requests for the original project's manifest. The starter prebundles React DOM's client entry so Astro can import its named exports in development.
  • Studio's source-editing mode discovered all 73 wrappers, inserted a HeroUI Button from the palette, and saved a dark overlay variable to the original site. The generated gallery also responded to a click on its hydrated Pin item toggle.
