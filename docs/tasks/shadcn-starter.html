Stacki shadcn starter tasks

Add a standalone shadcn Astro starter to Stacki. After creation, the site opens on Style Guide with Example Components in its navigation. The generated theme is editable through Variables, and each advertised starter component is insertable through Components.

This plan records the implementation order and acceptance checks for shadcn-starter. The implementation uses shadcn CLI 4.23.0.

  1. Verify the official CLI
  2. Define the starter request
  3. Create and open the site
  4. Add the welcome action and wizard
  5. Verify theme variables
  6. Prove palette insertion with Button
  7. Build both starter pages
  8. Verify the shipped component list
  9. Run contribution checks

Product decisions

Welcome and project type
Keep Lumos as the main action. Add Start from shadcn beside Start from Astro in its dropdown. Use the Lumos folder picker and wizard flow. Astro is fixed, and the starter creates one standalone site.
Project fields
Show Site name, a read-only Project path that updates with the name, and Stacki's existing Package manager dropdown. npm is the initial selection.
Base and icon library
Use visible single-select cards with monochrome SVG marks, full labels, and keyboard focus for both fields. Base UI is selected initially, with React Aria and Radix UI available. Icon choices are Lucide, Tabler Icons, Hugeicons, Phosphor Icons, and Remix Icon. Lucide is selected initially. Use the shadcn mark next to Start from shadcn in the welcome menu.
Preset and switches
Use Nova with the Neutral palette when the optional preset code is blank. A valid pasted code loads its theme and selects its icon library. A subsequent icon choice overrides that one field. Base, pointer cursor on buttons, and RTL support come from their own controls. Both switches start off. Enabling RTL support adds a reading direction control to the generated previews. A new preview still opens left to right. An invalid code gets an inline error.
After Create site
Show progress and open the live preview after setup succeeds. On failure, show the failed step and preserve the wizard input. The editor integration uses the starter, project CSS, and the existing Components and Variables tabs.

Marketplace apps add optional editor tools. Lumos Fluid Builder is independent of the Lumos starter. Marketplace packaging, UI SDK, monorepo generation, and a built-in copy of the shadcn theme configurator are outside this contribution. Stacki Apps guide

What the audit found

  • Stacki runs the Lumos generator, then applies project defaults, installs dependencies, and handles Git. The welcome wrapper passes one alternative action to a shared split button that already supports several. Starter runner · Project creation handlers · Welcome split button
  • The earlier official shadcn Astro run on Base UI and Nova produced a buildable site with React, Tailwind, a Button, a lockfile, and an initial commit. The CLI manages install and Git during creation. The remaining bases, icon overrides, and cross-platform manager behavior need verification. Official Astro setup · CLI options
  • Stacki reads authored CSS custom properties from source, including :root and .dark. The palette scans Astro files. shadcn generates React source and keeps CLI configuration in the root components.json. Stacki stores its insertion recipes in .stacki/components.json. Variable reader · Desktop discovery · Studio discovery · Project metadata

Tasks in implementation order

1. Verify the official CLI in disposable sites

Record the CLI version used for the contribution and make Astro and standalone generation explicit. Prove the effective package manager and lockfile for every manager exposed in the wizard, including a destination under a parent with different package-manager metadata. Check what the CLI installs and commits. Document the tested invocation so implementation can reuse it.

Use shadcn's preset tools to validate and resolve the optional code. For icon overrides, test the supported migrate icons command before installing the starter's component list. Verify it updates the generated config, imports, and dependencies without changing the selected theme. Use the resolved icon library for later additions. Address any unsupported icon mappings before exposing the corresponding choice.

Done when all three bases and five icon libraries have evidence from generated output. Cover the blank and custom presets, one conflicting icon override, pointer on and off, and RTL on and off. Check the generated CSS, config, and lockfile as well as a successful Astro build. Use a targeted matrix that covers each option and the interactions above. shadcn CLI · RTL conventions

2. Define the starter request and defaults

Read the shared contracts first. Model Lumos and shadcn requests as distinct variants and keep the shared package-manager and name rules. Validate base, icon library, preset code, path, and switches at the boundary. Share the option defaults between the renderer and main process. Separate an untouched preset-derived icon from an explicit user selection so a preset change updates the right field.

Done when focused contract tests accept every supported option and reject malformed requests, unknown values, oversized input, option-like values, and invalid codes. Existing Lumos requests still work. Stacki contracts · IPC payloads · Welcome bridge

3. Create and open the site safely

Reuse Stacki's subprocess, progress, tool-path, and project-default helpers where their behavior fits. Pass an argument list to the official CLI. Check required tools before writing. Confirm the CLI selected the requested manager before proceeding. Account for its own install and Git steps, preserve a coherent initial history of the finished site, and keep Git configuration and remotes local to the generated project.

Give each attempt an owned work location and refuse to replace existing files or links. Put the finished site at the requested path only after generation, theme setup, and starter content succeed. Verify relocatability for each manager before relying on a staged install. Bound subprocess duration and output. Wait for the attempt to stop writing before offering retry, and keep stale logs out of the next attempt. Preserve the existing Cancel behavior while creation runs.

Done when success returns a valid Astro path with the chosen lockfile and final starter files. Missing tools, timeout, invalid preset, a concurrent attempt, and a destination created during setup produce a clear outcome without overwriting user files. Confirm a failed install neither opens an incomplete site nor leaves the final path marked successful. Starter process runner · Existing project finalization · Starter tests

4. Add the welcome action and wizard

Pass multiple alternatives to the existing welcome split button. Open the parent-folder picker first. Reuse the existing wizard fields, custom Package manager dropdown, logs, and translations. Use labelled, keyboard-accessible single-select groups for Base and Icon library, plus the existing switch style for pointer and RTL. Link to shadcn Create beside the optional preset field.

Done when keyboard and mouse users can open the new flow, cancel the folder picker, edit options, and submit once. Verify the default and preset icon selection, an explicit icon override, both switches, validation feedback, progress, retry, and opening after success. Lumos and plain Astro retain their existing flows. Welcome screen · Existing wizard · Welcome tests

5. Verify light and dark theme variables

Keep shadcn's theme in the generated site's global stylesheet under src. Use the authored :root and .dark declarations for editable values. Preserve Tailwind's @theme inline aliases. Confirm each color token supplied by the selected theme appears under the correct scope in Variables, including background, foreground, primary, accent, chart, and sidebar colors when present.

Done when Desktop and Studio edit the same light and dark token independently, save only the intended declaration, and update the computed color on the page in the matching mode. Verify the saved values after reopen and exercise an outdated edit. If current Stacki misses a declaration, fix the shared reader or the generated CSS at the source. shadcn theme tokens · Studio variable operations

6. Prove palette insertion with Button

Keep the official React Button and add a thin, project-owned Astro wrapper. Expose an editable label and supported variant. Set useful insertion defaults in .stacki/components.json and use normal Astro props and slots. Keep Stacki markup out of Astro files.

Done when Button appears in Components in Desktop and Studio. Insert it into a test page, change label and variant, then check preview, saved source, undo and redo, and reopen. Confirm the generated shadcn source stays intact during instance edits. Repeat on all three bases before expanding the catalogue. Stacki component guide · Recipe validation

7. Build Style Guide and Example Components

Make Style Guide the homepage. Show semantic colors, typography, radius, and the selected icons alongside working controls. Use Example Components for a composed interface with realistic sample data. Use shadcn's Toggle Group for theme selection in the shared Astro layout and for LTR or RTL selection when the project enables RTL support. Remember each choice across navigation. Use the generated project's theme and registry components on both pages. shadcn Create preview reference

Done when a fresh install opens on Style Guide, both links work in the canvas, and the pages build as normal routes. Change a theme token and see it update in both. Check keyboard and focus behavior in a Dialog or another overlay, and verify that Tabs respond and retain saved defaults after reopen. Test RTL layout and overlay placement with Arabic content. Astro hydration

8. Verify every component shipped in the starter

Install every registry:ui entry supported by the selected base and let shadcn resolve its dependencies. The 4.23.0 registry contains 65 Base UI entries, 64 Radix UI entries, and 62 React Aria entries. Add the three documented compositions for Data Table, Date Picker, and Typography. Keep compound React widgets in one island where their parts share state. Use Astro wrappers and recipes for Components, and preserve the generated CSS variables and Tailwind theme aliases.

Done when the installed inventory and searchable Components entries match for every base. Test insertion of each advertised entry in Desktop and Studio, verify its default content and rendered output, and exercise interactive examples in the canvas. Run the installed astro-studio check-project <project-directory> on generated fixtures to catch missing paths, invalid slots, or cycles. Official component catalogue · Studio insertion tests · Studio preview checks

9. Run contribution checks

Read the repository instructions for the touched areas. Use the existing gates and hooks. Run npm run check:changed and env -u ELECTRON_RUN_AS_NODE npm test for the completed feature. Run the generated site's astro build through its chosen package manager. Run the existing Desktop and Studio browser checks that cover the changed paths. Create a fresh site through the actual welcome flow and record the exact base, preset, icon library, manager, and switches used.

Done when the tested checkout can create a site, open both pages, edit theme values, and insert the shipped components. Record any combinations still unverified before asking for review. Keep unrelated Builder changes, policy files, and generated preview output out of the contribution. Repository instructions · Checks and hooks

  • All six starter components saved through the Desktop and Studio palettes. A Button label and variant edit updated the Desktop canvas and Astro source. Light and dark color declarations saved independently in Studio.
  • Both starter pages rendered with working navigation and theme switching. Browser checks exercised Tabs and an Arabic RTL Dialog with focus return.
  • The full repository run reported an EmDash dialog layout failure that also reproduced on unchanged commit b36a2d02. The phone preview's skeleton timing failure also reproduced on that commit and passed an isolated branch rerun.
